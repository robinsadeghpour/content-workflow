#### Research Integration
- **D-06:** Research runs as the FIRST step in `/generate-content`, before any writer agent spawns. One research pass feeds all 4 platform drafts — consistent facts across TikTok EN/DE, Instagram, LinkedIn.
- **D-07:** Research artifact is a structured brief: key facts, 3–5 quotes/stats, sources list, angle suggestions. Writer picks what to use.
- **D-08:** Persistence path: `data/research/{idea_id}.md`. One file per idea, reusable across regenerate runs, visible in dashboard.
- **D-09:** Writer receives research by inlining the full brief into the writer agent prompt. No extra tool calls.

#### Writer-Critic Loop
- **D-10:** Hard iteration cap: **2 revisions max per platform** (initial write → critique → revise → critique → revise → critique → final).
- **D-11:** Pass bar: **≥ 8/10 on every scored dimension**. Exit loop as soon as all dimensions clear.
- **D-12:** On max-iters hit: keep the **best-scored iteration** (not necessarily the last), pass it through with a `did-not-pass` flag so Robin sees which drafts failed the bar.
- **D-13:** On revise, writer receives **full critic feedback + the previous draft** and produces a new full draft. This replaces the buggy `Object.assign(content, revisedContent)` shallow-merge at `scripts/apply-critic.js:242` (CR-01). The reviser's output fully replaces `content`, not merges.

#### Critic Rubric
- **D-14:** Critic scores exactly three dimensions: **Hook strength**, **Fact grounding**, **Slide/content economy**. Voice authenticity is dropped from the critic — it's already handled by the `/writing` + humanizer pass before the critic sees the draft.
- **D-15:** Per-platform rubric weights: TikTok weights hook + economy highest; LinkedIn weights fact-grounding highest. Each platform has its own weight vector.
- **D-16:** Fact grounding check: critic re-reads `data/research/{idea_id}.md` alongside the draft and flags any factual claim not supported by the brief. No inline citation markers required from the writer.
- **D-17:** Content economy enforcement: **cut-test per unit**. For each slide/paragraph the critic asks "if I removed this, would the draft be worse?" If not → recommend cut. No hard slide-count range; economy is a heuristic, not a fixed cap.

NotebookLM is accessed via the `notebooklm` CLI (Python-backed, installed at `/Users/robinsadeghpour/.local/bin/notebooklm`, version 0.3.3 verified). **Authentication:** `notebooklm login` (browser OAuth) → stores session in `~/.notebooklm/`. Verify with `notebooklm status`. [CITED: notebooklm-py/SKILL.md]

**Parallel-safe invocation pattern (required for 06.1, since orchestrator runs 4 writers):**
```bash
# Create notebook for this idea
NOTEBOOK_ID=$(notebooklm create "Research: $IDEA_TITLE" --json | jq -r .id)

# Add source URL(s) from the idea (YouTube transcripts, web pages, etc.)

# Wait for indexing (required before ask)
notebooklm source wait -n "$NOTEBOOK_ID" --timeout 120

# Synthesize the brief
notebooklm ask "Summarize key facts, 3-5 quotes/stats, and suggested content angles for Robin Faraj to post about this topic. Bias toward information from the last 30 days." -n "$NOTEBOOK_ID" --json
```

**Critical:** Use the `-n <notebook_id>` / `--notebook <notebook_id>` flag on every command. **Never rely on `notebooklm use`** in this pipeline — it stores context in `~/.notebooklm/context.json` which gets overwritten when multiple agents run in parallel. [CITED: notebooklm-py/SKILL.md §Parallel safety]

**Inputs accepted by NotebookLM:**
- URLs (web, YouTube, Google Docs) — `source add "https://..."`
- Local files — `source add ./path.pdf` (PDFs, text, Markdown, audio, video, images)
- Web research query — `source add-research "query"` (fast: 5-10 sources, seconds; deep: 20+ sources, 2-5 min)

**Output shape from `ask --json`:**
```json
{
  "answer": "X is... [1] [2]",
  "conversation_id": "...",
  "turn_number": 1,
```

The `answer` field is the synthesized text; `references` array gives source traceability for the fact-grounding check (D-16). [CITED: notebooklm-py/SKILL.md §Command Output Formats]

**Non-interactive verdict:** Yes — fully scriptable from bash with `--json` + `jq`. No TTY required. Exit codes are consistent (0=success, 1=error, 2=timeout on wait commands). [CITED: notebooklm-py/SKILL.md §Exit Codes]

### Q3: CR-01 exact repro (historical context)

Reading `git show HEAD:scripts/apply-critic.js` (lines 174-250):

```js
let content;                                                        // L174 — let, reassignable
content = safeJsonParse(draft.content, ...);                        // L175

while (!passed && attempts < MAX_ATTEMPTS) {                        // L197
  // ...critic call, parses criticResult...

  if (overall_pass) {
    passed = true;                                                  // L228
  } else if (attempts < MAX_ATTEMPTS) {
    // ...revise call, parses revisedContent...
    const revisedContent = safeJsonParse(reviseResponse...);        // L243

    db.prepare('UPDATE drafts SET content = ? ...')
      .run(JSON.stringify(revisedContent), draft.id);               // L246-247 — DB gets full replacement

    Object.assign(content, revisedContent);                         // L250 — BUG
  }
}
```

**The bug:** The DB write on L246 correctly persists the full replacement, but the in-memory `content` object used by the next loop iteration's critic call (`buildCriticUserPrompt(draft, content, idea)` at L207) is a Frankenstein of old + new keys. If `revisedContent` has fewer top-level keys than `content`, stale keys from the original persist. Nested objects are shallow-merged at the top level only — nested keys from the original survive into the hybrid. The critic then evaluates the hybrid, not the revised content.

**Shape examples:**
- `content` for tiktok_en: `{ slides: [...], caption, hook_formula }`
- If `revisedContent` omits `hook_formula` (reviser forgot), the old `hook_formula` sticks
- If `revisedContent` rewrites slides but keeps caption, the critic sees new slides + old caption — but only because both are top-level. A nested `slides[0].photo_description` change survives only because array assignment at the top level replaces the whole array.

**Fix:** `content = revisedContent;` (full reassignment). `let` on L174 makes this legal.

**But:** Because the scripts are deleted, this fix no longer applies to any running JS file. **The real fix** is in agent prompts — ensure the orchestrator treats the critic's revise-mode output as a complete replacement that flows forward to the next evaluate call. The orchestrator's Step 6 says "Spawn **critic** with mode: `revise`, passing the draft + feedback / Critic returns revised content / Re-spawn **critic** with mode: `evaluate` on revised content" — this is already correct semantically, but the planner must add an explicit rule: **"The revised content from revise mode is the new authoritative draft. Do not merge with the prior draft. Pass the exact JSON from the revise response as the `Draft content JSON` input to the next evaluate call."**

### Q6: Drafts persistence — schema migration?

**Current drafts schema** (verified via `sqlite3 .schema drafts`):
```sql
CREATE TABLE drafts (
  id, idea_id, platform, content, status, postiz_id,
  created_at, updated_at,
  visual_approach, media_dir, topic_category, original_content
);
```

No `research_thin` or `did_not_pass_critic` columns exist.

**Two viable approaches — planner picks one:**

**Option A: No migration, flags embedded in `content` JSON blob**
The `drafts.content` field is a JSON string, already mutated per-platform. Add top-level keys:
```json
{
  "type": "tiktok_slideshow",
  "slides": [...],
  "research_thin": true,
  "did_not_pass_critic": true,
  "critic_scores": { "hook": 7, "facts": 10, "economy": 6 },
  "critic_best_iteration": 2
}
```

Pros: Zero schema migration. Dashboard already reads `content` as JSON. `db-write-draft.js` requires no change.
Cons: Dashboard must parse JSON to filter drafts by flag. No indexed lookups.

**Option B: Add columns via idempotent ALTER TABLE**
Append to `scripts/init-db.js`:
```js
try { db.exec('ALTER TABLE drafts ADD COLUMN research_thin INTEGER DEFAULT 0'); } catch (e) { if (!e.message.includes('duplicate column')) throw e; }
try { db.exec('ALTER TABLE drafts ADD COLUMN did_not_pass_critic INTEGER DEFAULT 0'); } catch (e) { if (!e.message.includes('duplicate column')) throw e; }
```
Then extend `db-write-draft.js` to accept `--research-thin` and `--did-not-pass` flags.

Pros: Indexable. Dashboard can filter via plain SQL. Matches existing phase-3/phase-4 pattern of idempotent ALTERs.
Cons: Two schema changes, one new arg on db-write-draft.js, one SQL update path for the critic failure handler.

**Recommendation:** **Option B** — it matches the existing precedent in `init-db.js` (4 prior ALTER TABLE blocks for visual_approach, media_dir, topic_category, original_content). The dashboard API already does simple `WHERE status IN (...)` queries (see api.js:279); adding a `WHERE research_thin = 1` filter is trivial, but only with a real column.

### Q7: Supadata vs NotebookLM boundary

**Supadata is already used at pulse time** for transcript extraction via `scripts/pulse/transcript-fetcher.js` (per project SKILL descriptions) and the result lands in `ideas.transcript`. [VERIFIED: schema + SKILL.md]

**Decision for 06.1 research step:**

1. **Reuse `ideas.transcript` first.** If the idea row has a non-null transcript, write it to `/tmp/research-{idea_id}-transcript.txt` and add it as a local file source: `notebooklm source add /tmp/research-{idea_id}-transcript.txt --notebook $NB`.
2. **Add `source_url` as a second source** so NotebookLM can pull metadata, comments, or the raw page.
3. **Only then use `source add-research`** for supplementary web sources, to reach the 3-6 source target (D-03).

**Do NOT cache NotebookLM notebooks across runs.** Create a fresh notebook per idea per research pass. Rationale: idea re-runs should get fresh web research (D-04 freshness bias), and NotebookLM notebooks persist indefinitely, so stale notebooks pile up. Optional cleanup: `notebooklm delete <notebook_id>` at the end of the research step (but only after the brief is safely persisted to `data/research/{idea_id}.md`).

### Pattern 1: Research Pass (bash in orchestrator)
**What:** A bash block inside `content-orchestrator.md` Step 1.5 that uses NotebookLM CLI to produce the brief.
**When to use:** Once per `/generate-content` invocation, between idea load and visual-approach determination.

**Pseudocode:**
```bash
# Step 1.5 — Research Pass (D-06)
IDEA_ID="<uuid>"
IDEA_TITLE="<from idea row>"
IDEA_URL="<from idea row>"
IDEA_TRANSCRIPT="<from idea row, may be empty>"
BRIEF_PATH="data/research/${IDEA_ID}.md"

mkdir -p data/research

# Skip re-research if brief already exists and idea is being regenerated
if [ -f "$BRIEF_PATH" ]; then
  echo "Using cached research brief: $BRIEF_PATH"
else
  # Create fresh notebook
  NOTEBOOK_ID=$(notebooklm create "Research: $IDEA_TITLE" --json | jq -r .id)

  # Seed with known sources (cached transcript + source URL)
  if [ -n "$IDEA_TRANSCRIPT" ]; then
    TRANSCRIPT_TMP=$(mktemp --suffix=.txt)
    printf '%s' "$IDEA_TRANSCRIPT" > "$TRANSCRIPT_TMP"
    notebooklm source add "$TRANSCRIPT_TMP" -n "$NOTEBOOK_ID" --json || echo "[warn] transcript source failed"
  fi
  [ -n "$IDEA_URL" ] && notebooklm source add "$IDEA_URL" -n "$NOTEBOOK_ID" --json || true

  # Supplement with fresh web research (D-03: 3-6 sources, D-04: 30-day freshness)
  notebooklm source add-research "$IDEA_TITLE last 30 days" --mode fast -n "$NOTEBOOK_ID" --import-all || true

  # Wait for indexing (max 120s, fail open)
  notebooklm source wait -n "$NOTEBOOK_ID" --timeout 120 || RESEARCH_THIN=1

  # Synthesize
  BRIEF_JSON=$(notebooklm ask "Produce a research brief for Robin Faraj with: (1) 3-5 key facts, (2) 3-5 quotes or stats with attribution, (3) source list with publish dates, (4) 2-4 suggested content angles (contrarian, data-driven, story-driven). Bias toward info from the last 30 days. If you don't have enough information, say so explicitly." -n "$NOTEBOOK_ID" --json)

  ANSWER=$(echo "$BRIEF_JSON" | jq -r .answer)

  # Heuristic research-thin detection
  if [ ${#ANSWER} -lt 200 ] || echo "$ANSWER" | grep -qi "don't have enough"; then
    RESEARCH_THIN=1
  fi

  # Write the brief file
  cat > "$BRIEF_PATH" <<EOF
---
idea_id: $IDEA_ID
researched_at: $(date -u +%Y-%m-%dT%H:%M:%SZ)
research_thin: ${RESEARCH_THIN:-false}
notebooklm_notebook_id: $NOTEBOOK_ID
---

# Research Brief: $IDEA_TITLE

$ANSWER
EOF

  # Optional cleanup (keep for now — easier debugging)
  # notebooklm notebook delete "$NOTEBOOK_ID"
fi
```

### Pattern 3: Iteration Cap + Best-Iteration Retention (D-10, D-11, D-12)
In `content-orchestrator.md`, replace the current "up to 3 total attempts" language with:

```
Critic loop (per platform):
1. critic(evaluate, iteration=0) → scores_0
   If all dimensions >= 8, pass. Done.
2. critic(revise, with scores_0 feedback) → draft_1
3. critic(evaluate, iteration=1) → scores_1
   If all dimensions >= 8, pass. Done.
4. critic(revise, with scores_1 feedback) → draft_2
5. critic(evaluate, iteration=2) → scores_2
   If all dimensions >= 8, pass. Done.
6. Max revisions hit. Select best iteration by weighted-average score (use platform weights from critic-rubric.json). Mark did_not_pass_critic=true on the selected draft.
```

Track state across the loop:
- `attempts_history = [{draft: draft_0, scores: scores_0}, {draft: draft_1, scores: scores_1}, {draft: draft_2, scores: scores_2}]`
- `best = argmax(attempts_history, weighted_score(platform, scores))`

Persist `best.draft` as the final content, with flags.

### Pattern 4: Critic Rubric File (D-14, D-15, D-16, D-17)
`.claude/agents/data/critic-rubric.json`:
```json
{
  "pass_threshold": 8,
  "max_revisions": 2,
  "dimensions": ["hook", "facts", "economy"],
  "weights": {
    "tiktok_en":  { "hook": 0.45, "facts": 0.20, "economy": 0.35 },
    "tiktok_de":  { "hook": 0.45, "facts": 0.20, "economy": 0.35 },
    "instagram":  { "hook": 0.40, "facts": 0.25, "economy": 0.35 },
    "linkedin":   { "hook": 0.25, "facts": 0.50, "economy": 0.25 }
  }
}
```

Rewrite `critic.md` Mode: Evaluate section:
- **HOOK STRENGTH (0-10):** Does the first slide/first paragraph stop the scroll? Is there a pattern interrupt, a contrarian claim, a specific number, or an open loop? Weak hooks: generic statements, setup sentences, questions without stakes.
- **FACT GROUNDING (0-10):** Re-read `data/research/{idea_id}.md`. For each factual claim in the draft, verify it traces to the brief. Uncited claims score 0 on this dimension. If the brief has `research_thin: true`, allow claims from the idea's `summary`/`transcript` fields to pass.
- **CONTENT ECONOMY (0-10):** Cut-test each unit (slide for TikTok/Instagram/LinkedIn carousel; paragraph for LinkedIn text). For each unit, ask: "If I removed this, would the draft be worse?" Count the cut-viable units. Score = 10 - (cuts * 2), floored at 0. Don't apply any hard slide cap.

The pass bar is `score >= pass_threshold` on EVERY dimension (D-11 uses 8), not a weighted average — weights are tiebreakers for best-iteration selection only.

## Common Pitfalls

### Pitfall 1: Editing stale file paths
**What goes wrong:** Planner creates a task "Edit `scripts/apply-critic.js:242`" — but the file is deleted in the working tree.
**Why it happens:** `03-REVIEW.md` and `06.1-CONTEXT.md` both reference the old paths. They were written before the agent migration.
**How to avoid:** The CR-01 fix must be described as "edit `content-orchestrator.md` Step 6/9/13 to make revise-mode full-replacement explicit, cap iterations at 2, track best iteration." No JS edit.
**Warning signs:** A plan task that says "open scripts/apply-critic.js" without first running `git status` or checking file existence.

### Pitfall 2: NotebookLM context leakage with parallel agents
**What goes wrong:** Two `/generate-content` invocations run simultaneously. One calls `notebooklm use <A>`, the other `notebooklm use <B>`. Both then call `notebooklm ask` without `-n` — their answers come back from the wrong notebook.
**Why it happens:** `~/.notebooklm/context.json` is shared state. [CITED: notebooklm-py/SKILL.md §Parallel agents]
**How to avoid:** Never use `notebooklm use` in automation. Always pass `-n $NOTEBOOK_ID` or `--notebook $NOTEBOOK_ID` on every command.
**Warning signs:** Research brief mentions facts from a different idea entirely.

### Pitfall 3: NotebookLM auth expiry mid-pipeline
**What goes wrong:** `notebooklm ask` fails with auth error mid-run. Orchestrator halts with no brief.
**Why it happens:** Google session cookies expire. No auto-refresh.
**How to avoid:** The research step must wrap all notebooklm calls in a single try block. On auth error, set `RESEARCH_THIN=1`, write a minimal brief, continue (D-05 fallback path).
**Warning signs:** `AUTH/cookie error` in stderr.

### Pitfall 4: Slow NotebookLM indexing blocking the whole pipeline
**What goes wrong:** `source wait` times out at 120s, pipeline halts.
**Why it happens:** Source processing is 30s-10min. 120s is tight.
**How to avoid:** Use `--timeout 180`. Treat timeout (exit code 2) as research-thin, not fatal. Still write a minimal brief and continue.
**Warning signs:** Research step hangs for minutes on a single idea.

### Pitfall 5: Pass bar raised to 8 causes loop thrashing
**What goes wrong:** Threshold from 7 → 8 means many more drafts fail, and with the cap at 2 revisions, most drafts will exit as `did_not_pass_critic`.
**Why it happens:** 8/10 on Hook is subjective and hard to hit.
**How to avoid:** Run a smoke test on 3-5 kept ideas before treating 06.1 as done. If >50% of drafts fail, either loosen the rubric definitions or raise revision cap temporarily during tuning. The pass_threshold is in the config file, so it's a one-line tweak.
**Warning signs:** Every `/generate-content` run ends with 4 red badges on the dashboard.

### Pitfall 6: Writer not reading the brief
**What goes wrong:** Writer agent generates content that contradicts the research brief.
**Why it happens:** The writer agent has many "MANDATORY: Read X before Y" instructions and may skip one.
**How to avoid:** In `writer.md`, put the research brief read as the FIRST mandatory read (before voice profile). Make it fatal: "If you cannot read the brief, stop and report the error."
**Warning signs:** Critic fact-grounding scores are consistently low.

### Pitfall 7: Dashboard not showing flags because columns don't exist
**What goes wrong:** Option B (Q6) is chosen, but someone forgets to re-run `node scripts/init-db.js` after pulling the changes. The ALTER TABLE blocks never run → dashboard renders no badges.
**How to avoid:** Plan task should explicitly: (1) add ALTERs, (2) run `node scripts/init-db.js` as verification, (3) confirm with `sqlite3 data/content.db ".schema drafts"`.

### Example 2: Best-iteration selection (agent pseudocode)
```
weights = read_json(".claude/agents/data/critic-rubric.json").weights[platform]
iterations = []
for i in 0..max_revisions:
    scores = critic.evaluate(draft)
    iterations.append({draft, scores})
    if all(s >= 8 for s in scores.values()):
        return {draft, did_not_pass: false, flags: {...}}
    if i < max_revisions:
        draft = critic.revise(draft, scores.feedback)  // REPLACES draft wholesale (D-13)

// max_revisions hit
best = max(iterations, key=lambda it: sum(it.scores[d] * weights[d] for d in weights))
return {draft: best.draft, did_not_pass: true, flags: {critic_scores: best.scores}}
```
