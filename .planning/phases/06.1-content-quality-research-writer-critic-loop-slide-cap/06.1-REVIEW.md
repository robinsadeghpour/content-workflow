## Warnings

### WR-01: Orchestrator "NEVER use gpt-image-1.5" rule contradicts CLAUDE.md

**File:** `.claude/agents/content-orchestrator.md:285`
**Issue:** The Key Rules section states `**NEVER use gpt-image-1 or gpt-image-1.5** — AI slides use Gemini (D-01).` CLAUDE.md's technology stack explicitly mandates `gpt-image-1.5` for Larry's pipeline and warns that `gpt-image-1` is forbidden. A future agent reading both files will hit a direct contradiction. The orchestrator rule is technically correct for the Phase 06.1 Gemini-based pipeline, but the blanket wording is misleading without scoping context.
**Fix:** Scope the rule to this pipeline explicitly:
```markdown
- **This pipeline uses Gemini (nano-banana) for AI slide generation, NOT OpenAI gpt-image-*.** The Larry 1.0.0 pipeline in `Larry 1.0.0/` still uses `gpt-image-1.5`; do not conflate the two codebases.
```

### WR-02: NotebookLM heredoc vulnerable to early termination

**File:** `scripts/research/run-notebooklm.sh:121-132`
**Issue:** The brief is written via an unquoted heredoc `cat > "$BRIEF_PATH" <<EOF ... EOF`. If the NotebookLM answer ever contains a line consisting solely of `EOF`, the heredoc terminates early and the rest of the answer plus the closing delimiter become shell input, corrupting the brief file and potentially causing script errors. Low probability but not zero — models sometimes echo section markers. The same heredoc also re-expands `$(...)` and backticks found literally in `${ANSWER}`, although because ANSWER is first variable-expanded (not re-scanned for command substitution in standard bash), this is not a command-injection risk — only a content-corruption risk.
**Fix:** Use a guaranteed-unique sentinel and write via a temp + mv, or better, pipe via stdin:
```bash
{
  printf -- '---\nidea_id: %s\nresearched_at: %s\nresearch_thin: %s\nnotebooklm_notebook_id: %s\n---\n\n# Research Brief: %s\n\n' \
    "$IDEA_ID" "$RESEARCHED_AT" "$RESEARCH_THIN" "$NOTEBOOK_ID" "$IDEA_TITLE"
  printf '%s\n' "$ANSWER"
} > "$BRIEF_PATH"
```
This avoids heredoc delimiter collisions entirely and is robust to any answer content.

## Info

### IN-01: db-write-draft.js comment describes wrong SQL strategy

**File:** `scripts/db-write-draft.js:111`
**Issue:** Comment says `Upsert: INSERT OR REPLACE so repeated writes during writer-critic loop overwrite` but the actual SQL below uses `INSERT ... ON CONFLICT(id) DO UPDATE`. These are semantically different (REPLACE deletes+inserts, affecting foreign-key cascade and triggers; ON CONFLICT UPDATE preserves the row identity). The code is correct — the comment is stale.
**Fix:** Update the comment to `Upsert: INSERT ... ON CONFLICT DO UPDATE preserves row identity + created_at across writer-critic iterations.`

### IN-02: getArg silently swallows values starting with `--`

**File:** `scripts/db-write-draft.js:44-50`
**Issue:** `getArg` treats any value starting with `--` as "missing" and returns `''`. This means a legitimate value like `--content "--starts-with-dashes"` would be lost. Also means `--visual-approach --research-thin` returns `''` for visual-approach without warning. Acceptable for this CLI's call pattern (orchestrator passes known-safe values), but a footgun for future callers.
**Fix:** Either document the constraint in the usage header, or accept the next token literally and rely on required-field validation.

### IN-03: NotebookLM frontmatter emits empty notebook id on fail-open

**File:** `scripts/research/run-notebooklm.sh:126`
**Issue:** When `notebooklm create` fails, `NOTEBOOK_ID=""` and the frontmatter line becomes `notebooklm_notebook_id:` (empty value). This parses as `null` in most YAML parsers but looks sketchy in the dashboard and could trip a strict reader.
**Fix:** Emit `notebooklm_notebook_id: ${NOTEBOOK_ID:-none}` or wrap in quotes.

### IN-04: Hardcoded English string used for thin-detection

**File:** `scripts/research/run-notebooklm.sh:109`
**Issue:** `grep -qi "don't have enough"` matches only English refusals. If NotebookLM ever replies in another language (unlikely but possible for German sources), thin detection silently fails. Heuristic is documented in SUMMARY so this is intentional, but worth flagging.
**Fix:** Add a second pattern for common refusal phrases, or rely solely on the length + empty checks already in place.

### IN-05: Orchestrator Step 1.5 bash template uses `<idea.transcript>` placeholder inside double quotes

**File:** `.claude/agents/content-orchestrator.md:95-98`
**Issue:** The template shows `printf '%s' "<idea.transcript>" > "$TRANSCRIPT_TMP"`. A future agent executing this literally with a transcript containing `"` will break quoting. The orchestrator is expected to substitute safely, but the example could mislead. Same applies to the `run-notebooklm.sh` invocation example where `<idea.title>` may contain `"` or `$`.
**Fix:** Add a note: `"Pass transcript via heredoc or printf argv, not interpolated into a double-quoted string, to avoid quote-escaping bugs when transcripts contain quotes or backticks."`

### IN-06: Dashboard badges use light colors on a dark-themed UI

**File:** `scripts/dashboard/public/style.css:552-561`
**Issue:** New badges use solid light backgrounds (`#fef3c7` amber, `#fee2e2` red) and dark text (`#92400e`, `#991b1b`), while every other badge on the page uses `color-mix(in oklab, var(--amber) 15%, transparent)` with CSS custom-property theming. The new badges will look jarring against the dark dashboard and won't respond to any future theme changes. Probably intentional for high-visibility advisory signaling, but inconsistent with the design system.
**Fix:** Match the existing pattern:
```css
.badge--research-thin {
  background: color-mix(in oklab, var(--amber) 18%, transparent);
  color: #fcd34d;
  border: 1px solid color-mix(in oklab, var(--amber) 35%, transparent);
}
.badge--did-not-pass {
  background: color-mix(in oklab, #ef4444 18%, transparent);
  color: #fca5a5;
  border: 1px solid color-mix(in oklab, #ef4444 35%, transparent);
}
```
